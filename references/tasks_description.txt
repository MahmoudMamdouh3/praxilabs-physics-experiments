## PRAXILABS TAKE-HOME ASSESSMENT — TASK 2

* **ROLE LEVEL:** Mid frontend / 3D developer


* **TIMEBOX:** 2–3 days


* **CORE STACK:** Three.js, JavaScript or TypeScript, any bundler (Vite recommended)


* **THEME:** A mini virtual physics lab platform with three swappable experiments



---

### Goal

Build a small physics-lab platform: three classic experiments running on one shared framework. The architecture is the point — the experiments must be interchangeable modules sharing a common interface, UI, and graphing system, and the physics must be numerically correct.

The platform must also be extensible by an AI agent. After you submit, we will take a specification for a physics experiment you have never seen, hand it to an AI agent together with your repository, and give it no hints from us — no walkthrough, no pointers, nothing beyond what is committed. We then score how cleanly that experiment drops into your platform. The fewer core and framework files it has to touch, the better you score.

---

### Required Scope

#### 1. Shared Framework (Mandatory Architecture)

* A common `Experiment` interface: `setup`, `update(dt)`, `reset`, `getMeasurements`, and a declared parameter schema.


* A UI panel that auto-generates sliders/inputs from each experiment's parameter schema — no per-experiment hand-built UI.


* A shared graphing module (2D overlay is fine) that plots any recorded quantity vs. time, with CSV export of the recorded data.


* A fixed-timestep simulation loop decoupled from the render loop (accumulator pattern). This will be checked: physics results must not change with frame rate.


* An experiment switcher in the UI that cleanly disposes one experiment and loads another (watch for Three.js resource leaks — geometries/materials `dispose`).



> The framework contract must be discoverable and extensible by an AI agent working alone. Assume a fourth experiment will be added later by an agent that has only your repository to go on: the interface, the registration point for a new experiment, and the conventions it must follow should be findable and unambiguous from the code and documentation as committed.

#### 2. Experiment A – Pendulum

* Simulated from the real equation of motion ($\theta'' = -(g/L) \cdot \sin\theta - \text{damping}$) — not small-angle shortcut, not a canned animation.
* **Parameters:** length, gravity, initial angle, damping.
* **Graph:** angle vs. time.
* A **'Measure period'** feature that computes the period from simulation data and displays it next to the theoretical $2\pi\sqrt{L/g}$, with % difference.

#### 3. Experiment B – Projectile Motion

* **Parameters:** launch angle, initial speed, gravity, optional air-resistance coefficient.
* **Before launch:** show the predicted analytic trajectory (no drag) as a dotted curve.
* **On launch:** simulate actual flight (with drag if enabled), mark the landing point, and display predicted vs. actual range.

#### 4. Experiment C – Spring-Mass Oscillator

* **Parameters:** spring constant $k$, mass, damping, initial displacement.
* Visible spring that stretches/compresses.
* **Graph:** displacement vs. time.
* Display measured vs. theoretical frequency ($\sqrt{k/m} / 2\pi$) for the undamped case.

#### 5. Numerical Integration

* Choose your integrator deliberately (semi-implicit Euler, $RK_4$, ...) and justify the choice in the `README`, including why plain explicit Euler is problematic for oscillators.
* Physics functions must be separated from rendering so they are testable without a browser canvas.

### Bonus (Only if core is complete)

* **Comparison mode:** run two parameter sets of the same experiment side by side.
* Unit tests on the physics functions (e.g., Vitest).
* **Energy plot** (kinetic/potential/total) demonstrating conservation quality of your integrator.

### Constraints & Rules

* **Timebox:** 2–3 days of effort. Submit what you have at the deadline; scoping decisions are part of the evaluation.
* Three.js is required for all 3D rendering. Physics/math must be your own or AI-assisted code — no physics engines (no cannon.js, rapier, etc.) unless the brief says otherwise.
* Keep third-party dependencies minimal and justify each one in the `README`.
* **Target:** recent Chrome/Firefox on desktop. Mobile support is not required.

---

### Deliverables

* **Git Repository:** Clear, incremental commit history. A single giant commit is not acceptable.
* **`README.md` covering:**
* How to run the project.
* Architecture overview and key decisions.
* Known limitations and what you would do next with more time.


* **`AI_USAGE.md` documenting your AI workflow:**
* Which tools and models you used (Claude, Copilot, ChatGPT, etc.).
* 3–5 representative prompts.
* At least two concrete cases where the AI output was wrong or suboptimal and how you detected and fixed it.
* Which parts you wrote fully by hand.
* Answer to: *What did you set up before writing any code, and why?*


* **Your Agent Environment (Mandatory):**
* Commit the persistent configuration given to your AI tooling into a directory in the repo (e.g., `.claude/`, `.agents/`, `.cursor/`, `.github/`).
* Rules, instructions, workflows, subagent definitions, MCP configuration, or whatever reusable components you used.
* Explain in `README` or in that directory what each piece was for, including at least one rule added because the AI kept getting something wrong.
* Commit as you go, not at the end.


* **Runnable App:** Must run with a simple, documented command (e.g., `npm install && npm run dev`). Vite + vanilla JS/TS or any framework is fine; Three.js must be the 3D engine.

### Review Session

After submission, there will be a ~30-minute call. You will walk through the architecture and make a small live modification chosen on the spot. Be sure you deeply understand every part of your codebase, including AI-generated parts.

#### A Note on AI Tools

You are encouraged to use AI assistants — this assessment explicitly measures how well you work with them. We are not testing whether you can avoid AI; we are testing whether you can direct it, verify it, and keep the codebase coherent. Blindly pasted AI output is easy to spot in the review session and will count against you.
